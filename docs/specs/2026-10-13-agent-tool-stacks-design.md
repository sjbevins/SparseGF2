# Agent tool stacks and research additions: design

Status: **proposed**, 2026-10-13. Branch `agent-stacks` (off `v3`).
Related: [`2026-10-13-reverse-log-design.md`](2026-10-13-reverse-log-design.md)
(deferred), [`../DESIGN.md`](../DESIGN.md) (architecture of the simulator).

## 1. Goal

Make the SparseGF2 MCP server genuinely useful for the erasure-protection
research workflow when it is driven by **mid-size local models** (through
Clank, Sam's local agent app) and by **Claude Code**, and let Sam assemble
and save his own **tool stacks** as models and tasks change.

The research workflow it must serve: codes generated by monitored random
Clifford circuits in the purification picture, on ensembles of
Watts-Strogatz small-world graphs (and any other geometry), studied through
random erasure: for a uniformly random ordering pi of the qubits and the
nested regions A_m = {pi_1, ..., pi_m}, the first-failure size
D_C(pi) = min{m : l_C(A_m) > 0}, P_C(m) = Pr[D_C <= m], and the failure
probability under independent erasure at rate e,
Phi_C(e) = E_D[Pr{Bin(n, e) >= D}], estimated from M orderings by
Phi_C(e) ~ (1/M) sum_j Pr{Bin(n, e) >= D_j}. Contiguous distance stays
available but is not featured.

## 2. Success criteria

1. **Flat schemas.** Every tool in the built-in stacks except `ensemble`
   has an input schema whose properties are all `string`, `integer`,
   `number`, `boolean`, a string `enum`, or an `array` of one of those. No
   nested objects, `$ref`, `$defs`, `oneOf`, `anyOf` or `allOf`; optional
   parameters are simply not `required` (never `anyOf [T, null]`). Enforced
   by a test over the tool registry.
2. **Small tool list.** The `research` stack's `tools/list` (names,
   descriptions, schemas, as JSON) is at most 16,000 characters (about
   4,000 tokens, under 10% of a 45k context). Enforced by a test. Today's 10
   tools are 9,900 characters with an untyped `spec`. Parameter
   descriptions stay terse (`help_topic` carries the detail), and a custom
   stack's `fixed` values shrink the list further.
3. **Self-contained text results.** Every result is plain text whose first
   line names the tool and what ran, ends with a `next:` line when there is a
   natural follow-up, and fits `--max-output-chars` (default 4,000). The same
   data is attached as `structuredContent` for clients that use it; nothing
   depends on a client reading it.
4. **The erasure workflow end to end through tools.** Running an ensemble,
   getting k/n, q+, mu_D, distance bounds, Phi(e) (all codes and k > 0),
   e_delta and P_C(m) per depth, sweeping one parameter, inspecting one
   trajectory and re-analysing a saved code all work without writing Python.
5. **Custom stacks.** `sparsegf2 stacks save|list|show|delete` creates and
   manages named stacks in a JSON file; a stack can combine built-in stacks
   and single tools, pin argument values (removed from the schema) and
   change defaults. `sparsegf2-mcp --stack NAME` serves it.
6. **Runs in Clank's sandbox.** Starts and answers `tools/list` in under 5 s
   with no network, accepts `--quiet`, keeps stdout to JSON-RPC, confines
   file access to `--root`, and ships a `sparsegf2 warmup` command that
   compiles every kernel into the Numba cache ahead of time.
7. **Measured usefulness.** `scripts/eval_agent_tools.py` runs a fixed set of
   research requests against any OpenAI-compatible endpoint (Clank's gateway,
   Ollama, ...) and reports how often the model picks the right tool with
   schema-valid arguments. Not a CI gate; it is how descriptions get tuned.

## 3. Constraints from the clients

**Clank** (github.com/sjbevins/Clank, read 2026-10-13). The agent loop is
OpenCode inside a per-workspace Docker sandbox (Ubuntu 24.04, Python 3.12,
no outbound network, half the cores, no GPU; only the workspace is mounted,
at `/workspace`). Models run on Clank's llama.cpp-family engines; the
catalogued model is Qwen3.8-27B with a 45,056-token context on the realistic
preset. Consequences:

* The model sees each tool's `name`, `description` and `inputSchema`, and the
  result's text. No `outputSchema`, `structuredContent`, annotations,
  progress, cancellation or `tools/list_changed`. So stacks are fixed when the
  server starts, and results must read well as text.
* The server must be installed in the image or the workspace and must not
  download anything; Numba's cache must live somewhere persistent and
  writable (`NUMBA_CACHE_DIR`).
* Long work must be start / poll / fetch, never one long blocking call.
* Clank's console launches `sparsegf2-mcp --quiet` by default.
* Stacks will most likely be switched per Clank mode through OpenCode's
  per-agent tool enablement, which matches tools by name pattern. Hence
  **every tool name starts with its stack's prefix**.

**Claude Code** reads the project `.mcp.json`. It copes with nested schemas,
so it gets every stack (`--stack all`), including the typed general
`ensemble` tools.

## 4. Architecture

```text
sparsegf2-mcp --stack research --root . [--stacks-file F] [--quiet] [--max-output-chars N]
        |
        v
agent.server   low-level mcp Server: on_list_tools / on_call_tool from the resolved stack
        |
agent.stacks   built-in stacks + bundles + custom stacks (JSON) -> list of (ToolDef, overrides)
        |
agent.registry ToolDef: name, stack, description, Params (flat JSON-schema types), handler
        |
handlers       agent/erasure.py, trajectory.py, codes.py, graphs.py, jobs.py, circuits.py,
               ensemble.py: JSON-in / dict-out, built on the library and sparsegf2.api
        |
agent.render   dict -> compact text (tables, +-, next: hints), capped at max_output_chars
```

* **Low-level server.** `mcp.server.lowlevel.Server(on_list_tools=...,
  on_call_tool=...)` (SDK 2.3) with hand-written JSON schemas, instead of
  `MCPServer`'s signature-derived ones. This is what lets a custom stack pin
  or re-default arguments and what keeps schemas flat.
* **Registry.** A `Param` is `(name, type, description, default, enum,
  minimum, maximum, items)` with `type` in `string | integer | number |
  boolean | array`. A `ToolDef` is `(name, stack, description, params,
  handler, read_only, nested_ok)`. Schemas are generated from these; the
  handler receives validated, defaulted keyword arguments.
* **One implementation.** Handlers return plain dicts and raise
  `ValueError` with a message saying what to change; the server turns those
  into tool errors. The CLI can expose the same handlers later; `api.py`
  keeps its current functions and gains no new responsibilities (it is
  already 2,700 lines).
* `mcp_server.py` stays as the entry point (`sparsegf2-mcp`) and delegates
  to `agent.server.main`.

## 5. Built-in stacks and tools

Tool name = `<stack>_<verb>`. Bundles: **`research`** (default when no
`--stack` is given) = `help`, `erasure`, `traj`, `code`, `graph`, `job`;
**`all`** = every stack. The repository's `.mcp.json` passes `--stack all`.

| stack | tools | for |
|---|---|---|
| `help` | `help_topic` | conventions on demand |
| `erasure` | `erasure_run`, `erasure_report`, `erasure_sweep` | the erasure workflow on ensembles |
| `traj` | `traj_run`, `traj_probe` | one trajectory: its code, probed at any depths, Stim cross-check |
| `code` | `code_analyze` | erasure analysis of a given or saved code |
| `graph` | `graph_stats` | statistics of a graph collection |
| `job` | `job_status`, `job_cancel`, `job_list` | background work |
| `ensemble` | `ensemble_run`, `ensemble_estimate`, `ensemble_start`, `ensemble_load` | the general engine, typed nested spec (Claude Code) |
| `circuit` | `circuit_inspect`, `circuit_run` | Stim-language circuits (today's tools) |

### 5.1 Shared parameter groups

Defined once in the registry and reused, so their names, meanings and
defaults are identical everywhere.

**Graph** (`erasure_run`, `erasure_sweep`, `traj_run`, `graph_stats`):

| param | type | default | meaning |
|---|---|---|---|
| `graph` | enum `watts_strogatz`, `newman_watts`, `cycle`, `random_regular`, `erdos_renyi`, `lattice_2d`, `complete`, `file` | `watts_strogatz` | family, or `file` for any geometry |
| `degree` | integer | 4 | total degree K (K/2 neighbours per side) for `watts_strogatz` / `newman_watts`; d for `random_regular` |
| `beta` | number | 0.1 | rewiring probability (`watts_strogatz`), shortcut probability per edge (`newman_watts`) |
| `edge_prob` | number | none | edge probability (`erdos_renyi`, required there) |
| `rows`, `cols` | integer | none | `lattice_2d` shape (rows * cols = n) |
| `graph_file` | string | none | path under `--root` of a JSON or NPZ graph collection (section 6.3), required for `file` |
| `graphs` | integer | 50 | number of graph realizations G (ignored for deterministic families and files, which fix their own count) |
| `graph_seed` | integer | 0 | graph i is drawn from seed (graph_seed, i); separate from the circuit seed |

A parameter given explicitly that does not apply to the chosen family is
an error, not silently ignored (`beta given for graph=cycle`), so the model
learns. Defaults never trigger this.

**Protocol** (`erasure_run`, `erasure_sweep`, `traj_run`): `n` (integer,
required), `p` (number in [0, 1], required: measurement rate),
`layers` (integer, required: depth T, one layer = gates then measurements,
never rescaled), `schedule` (enum `random_edges` | `matching` |
`all_edges`, default `random_edges`: n/2 random edges per layer with
replacement), `circuits_per_graph` (integer, default 4), `seed` (integer;
omitted = drawn and reported). Erasure tools fix `reference="purification"`;
`traj_run` takes `reference` (enum `purification` | `single` | `none`,
default `purification`).

**Depths:** `depths`, an array of layers in [0, layers]; omitted = the final
layer only. Layer 0 is the state after setup.

**Erasure analysis** (`erasure_run`, `erasure_report`, `erasure_sweep`,
`traj_run`, `traj_probe`, `code_analyze`): `orderings` (integer M, default
512), `exhaustive_size` (integer w, default 2: every erasure of up to w
qubits is checked exactly), `erasure_rates` (array of numbers, default
`[0.01, 0.02, 0.05, 0.1]`), `delta` (number, default 0.01: e_delta =
sup{e : Phi(e) <= delta}).

**Output:** `output_dir` (string under `--root`; default
`runs/<tool>-<hash of the arguments>`, so rerunning the same request reuses
and resumes the same directory).

### 5.2 `erasure_run`

Runs the ensemble with probes `code_dimension` (every evaluated depth),
`erasure_first_failure(orderings)`, `uncorrectable_region_counts(w)` at
`depths`, and `code_snapshot` at the final depth when `save_codes` (boolean,
default true). If the estimate exceeds `--sync-seconds` (default 60) it
starts a background job instead and returns its `job_id`, the
`output_dir` and the estimate; otherwise it returns the report of 5.3. The
result is always saved (`result.npz`, `spec.json`, `provenance.json`).

Example result:

```text
erasure_run: n=128, watts_strogatz(K=4, beta=0.1), 50 graphs x 4 circuits = 200 trajectories, p=0.1, layers=512 -> runs/erasure-3f2a9c
depth  k/n            q+     mu_D(k>0)    d<=2(k>0)  Phi(0.01)      Phi(0.05)      e_0.01(k>0)
  512  0.083+-0.004   0.97   12.3+-0.4    0.12       0.003+-0.001   0.041+-0.006   0.018
P_C(m), depth 512, k>0, m=1..16: 0 0.004 0.011 0.02 ...
next: erasure_report(output_dir="runs/erasure-3f2a9c", erasure_rates=[...]) for other rates or depths; traj_run(...) to inspect one trajectory
```

### 5.3 `erasure_report`

From a saved run (`output_dir`; any ensemble result with first-failure data
works). Parameters: the erasure-analysis group, `depths` (default all
evaluated), `show_pcm` (boolean, default true). Both conditionings are
always shown where they differ: over all circuits (a purified circuit, k = 0,
counts as protected) and over codes with k > 0. Per depth:
k/n, q+ (fraction with k > 0), mu_D, distance statistics, Phi(e) at each
rate (all and k > 0), e_delta (k > 0), and P_C(m) at the last depth
(compressed: m = 1..min(n, 32) and coarser beyond). For a sweep directory
(5.4) it returns one comparison table, one row per swept value.

Estimators (section 6.1): the hybrid estimator, exact for m <= w from the
exhaustive counts and sampled above from the orderings; standard errors
over trajectories.

### 5.4 `erasure_sweep`

`vary` (enum `p` | `beta` | `n` | `degree` | `layers`), `values` (array of
numbers, 2 to 32 entries), plus everything `erasure_run` takes. The varied
parameter must be left out (giving it is an error that says so); `n`, `p`
and `layers` are therefore optional in this schema and checked by the
handler. Always a background job: each point runs as a
chunked ensemble saved under `output_dir/<vary>=<value>/`, sequentially.
Points reuse the graph seeds (the same graph collection at every `p`) and
the circuit seed (the qubits measured at a lower p are a subset of those at
a higher one). Returns the `job_id` immediately; `job_status` shows
`points_done / points_total`; `erasure_report(output_dir)` gives the table.
For `vary=n` with `depths` given, depths must be valid for every n
(otherwise an error suggests leaving `depths` out).

### 5.5 `traj_run`

One trajectory, defined by the protocol and graph groups plus `trajectory`
(integer, default 0: which trajectory of the ensemble with this seed, so
any trajectory seen in an `erasure_run` can be pulled out) and `reference`.
By default it **only stores the code** at each requested depth and reports
`n, k` (free). Opt-in `properties` (array of enum):

| property | how |
|---|---|
| `first_failure` | `erasure_first_failure(orderings)`: D samples, mu_D, P_C(m) |
| `failure_probability` | Phi(e) and e_delta from the above (implies `first_failure`) |
| `exhaustive_counts` | `uncorrectable_region_counts(w)`: exact P_C(m), m <= w |
| `distance` | bounds from the above: d exact if <= w, else w < d <= min_j D_j (implies both) |
| `contiguous_distance` | the contiguous distance probe |
| `entanglement` | half-cut entropy |
| `stabilizer_weights` | weight histogram of the code's generators |
| `stabilizers` | the generators as Pauli strings (n <= 32 only) |

`compare_stim` (boolean, default false): exports the trajectory's exact
circuit (`MonitoredCircuit.circuit`), runs it in Stim's `TableauSimulator`,
and compares the final stabilizer group with SparseGF2's (canonical row
echelon forms) at every requested depth; reports `stim: match` or the first
mismatch. Needs Stim installed (the error says how). `save_circuit`
(boolean, default false) writes `circuit.stim`.

Saved: `trajectory.json` (protocol, graph, seed, trajectory index, package
version, randomness-contract version), `codes.npz` (the code at each depth).
This record is enough to replay the trajectory exactly (section 6.4).

### 5.6 `traj_probe`

`output_dir` of a `traj_run`, `properties`, `depths`, and the analysis
group. Replays the recorded trajectory with the new probes at the new depths
(section 6.4) and reports as `traj_run` does. This is "probe the trajectory
as a function of depth" after the fact.

### 5.7 `code_analyze`

A code from `stabilizers` (array of Pauli strings, e.g. `["XXXX","ZZZZ"]`)
or from `source` (a `traj_run` or ensemble `output_dir`) with `trajectory`
(row, default 0) and `depth` (default the last saved). `properties` as in
`traj_run` minus `contiguous_distance` and `entanglement` (they need the
state's qubit layout, not just the code). Uses `StabilizerCode`
(`first_failure_sizes`, `uncorrectable_counts`, `lost_information`).
`erasure` (array of qubit indices, optional): report l(A) for that region.

### 5.8 `graph_stats`

The graph group (built-in family or `graph_file`) plus `n`. Per collection,
mean +- standard error over graphs of: algebraic connectivity lambda_2 of
the Laplacian, fraction of connected graphs, mean shortest-path length
(connected graphs), average clustering coefficient, degree min / mean /
max, and for `watts_strogatz` / `newman_watts` the fraction of shortcut
edges (ring distance > K/2). lambda_2 uses a dense eigensolver: n <= 4096.

### 5.9 `job_*`, `help_topic`, `ensemble_*`, `circuit_*`

* `job_status(job_id, wait_seconds 0..60)`, `job_cancel(job_id)`,
  `job_list()`: today's job tools, extended to sweep jobs (points done),
  with `next:` pointing at `erasure_report` for erasure jobs. Jobs live in
  the server process; a restart loses the ids, not the saved chunks: calling
  the same `erasure_run` / `erasure_sweep` again resumes, because the
  default `output_dir` is a hash of the arguments.
* `help_topic(topic)`, `topic` enum `conventions` | `erasure` | `graphs` |
  `depth` | `jobs` | `stacks`: short markdown from the docs (a few hundred
  words each), so a model without the server's `instructions` can learn the
  conventions.
* `ensemble_run`, `ensemble_estimate`, `ensemble_start`, `ensemble_load`:
  today's `run_ensemble`, `estimate_ensemble`, `start_ensemble_job`,
  `load_results`, with `spec` given a real JSON schema generated from
  `MonitoredCircuit`'s fields (types, enums, the probe list as objects with
  a `kind` enum) instead of `additionalProperties: true`. `nested_ok`.
* `circuit_inspect`, `circuit_run`: today's `inspect_circuit`, `run_circuit`.

Today's tool names (`run_circuit`, ...) are removed, not aliased: there is
one user, and aliases would double the tool list.

## 6. Library additions

### 6.1 `sparsegf2.analysis`

* `mean_first_failure(first_failure, num_qubits, *, exact_counts=None)`:
  mu_D = E[D] = sum_{m=0}^{n} (1 - P_C(m)), computed from the same hybrid
  P_C(m) as `erasure_failure_probability`, so mu_D and Phi(e) never
  disagree. A k = 0 code (D = n + 1) gives n + 1; reports condition on
  k > 0.
* `distance_bounds(first_failure, exact_counts)`: per code `(low, high)`.
  An erasure of fewer than d qubits is always correctable, so every D_j >= d
  and `high = min_j D_j`. With counts up to w: if some count is positive,
  d is the smallest such m (`low = high = d`); otherwise `low = w + 1`. A
  k = 0 code has no distance: `(n + 1, n + 1)`, excluded by the reports.
* The hybrid P_C(m) (exact for m <= w, sampled above) can dip at the
  junction m = w + 1 through sampling noise. The estimators stay unbiased
  (no clipping); `erasure_report` flags a dip and suggests more `orderings`.

### 6.2 `sparsegf2.graphs`: statistics

`stats(edges, n)` -> dict with `lambda2`, `connected`, `mean_path_length`
(BFS from every node; NaN if disconnected), `clustering`, `degree_min`,
`degree_mean`, `degree_max`; `shortcut_fraction(edges, n, k)` for ring-based
families. Plain NumPy, no new dependency.

### 6.3 `sparsegf2.graphs`: files

`save(path, graphs, num_nodes)` and `load(path) -> (num_nodes, list of edge
arrays)`.

* JSON: `{"num_nodes": n, "edges": [[a, b], ...]}` for one graph, or
  `{"num_nodes": n, "graphs": [[[a, b], ...], ...]}` for a collection.
* NPZ: `num_nodes` (scalar), `edges` (E x 2 int64) and, for a collection,
  `ptr` (G + 1 offsets into `edges`).

Validation: integer nodes in [0, n), no self-loops, no repeated edge within
a graph, `num_nodes` equal to the requested `n`. Errors name the graph and
edge. The JSON API's spec accepts `"graph": {"family": "file", "path": ...}`,
so the same files work in the `ensemble` stack and in Python.

### 6.4 Replay (depth probing)

The randomness contract already makes trajectory t of `run(seed=s)` a
function of `(protocol, s, t)` only; it was verified on 2026-10-13 that
changing probes or checkpoints leaves even the generator matrices
bit-identical. So recording a trajectory = recording `(protocol, s, t)`, and
probing it at new depths = re-running it with new probes:

* `MonitoredCircuit.replay(trajectory, *, seed, probes, checkpoints)`
  returns a one-row `EnsembleResult`: `dataclasses.replace(self,
  probes=..., checkpoints=...).run(1, seed=seed, first_trajectory=trajectory)`.
* A test pins the contract (probes and checkpoints never change a
  trajectory), so replay cannot silently break.
* `trajectory.json` stores `randomness_contract` (an integer, now 1, bumped
  whenever the engine's random streams change); `traj_probe` refuses to
  replay a record from another contract version and says so.

Cost, measured (n = 256, T = 256, p = 0.1, one thread): the whole trajectory
simulates in 4.5 ms; one first-failure evaluation with M = 512 costs 5.2 ms.
The probes dominate, so replay costs about as much as one extra probe
evaluation. (Why not walk backward from the final tableau instead: see the
reverse-log spec, deferred.)

### 6.5 Stim comparison

`sparsegf2.crosscheck.stim_codes(circuit, ticks)` (imports Stim lazily):
runs the circuit in `stim.TableauSimulator`, reads the stabilizers after the
given ticks and returns them in the same canonical form as SparseGF2's, so
`traj_run` compares the stabilizer groups exactly (phases ignored: the
engine is phase-free).

## 7. Custom stacks

### 7.1 File

`stacks.json`, found in order: `--stacks-file PATH`; `<root>/.sparsegf2/
stacks.json` (project); the user file (`%APPDATA%\sparsegf2\stacks.json` on
Windows, `$XDG_CONFIG_HOME/sparsegf2/stacks.json` or
`~/.config/sparsegf2/stacks.json` elsewhere). A name found in an earlier
file wins. Custom names may not reuse a built-in stack or bundle name.

```json
{
  "version": 1,
  "stacks": {
    "ws-erasure": {
      "description": "WS K=4 erasure studies, n=128",
      "include": ["erasure", "job", "traj_run"],
      "exclude": ["erasure_sweep"],
      "fixed": {"*": {"graph": "watts_strogatz", "degree": 4, "n": 128}},
      "defaults": {"erasure_run": {"orderings": 1024}}
    }
  }
}
```

* `include`: built-in stacks, bundles, other custom stacks, or tool names.
* `exclude`: tool names removed after `include`.
* `fixed`: per tool (`"*"` = every tool in the stack that has the
  parameter) parameter values that are injected and **removed from the
  schema**. Smaller schemas are the strongest lever for weaker models.
* `defaults`: new defaults shown in the schema; still overridable.
* A stack containing a tool that can start background jobs (`erasure_run`,
  `erasure_sweep`, `ensemble_start`) automatically includes `job_status`.
* Validation at load: unknown stacks, tools or parameters, values that fail
  the parameter's type or enum, and cycles are errors that name the stack.

### 7.2 CLI

```text
sparsegf2 stacks list                       built-in and custom, with tool counts and schema size
sparsegf2 stacks show NAME                  its tools, fixed and default values, tools/list size
sparsegf2 stacks save NAME --include erasure,job,traj_run [--exclude T,...]
                     [--fix TOOL.PARAM=VALUE ...] [--default TOOL.PARAM=VALUE ...]
                     [--description TEXT] [--project | --user]
sparsegf2 stacks delete NAME [--project | --user]
```

`TOOL` may be `*`; `VALUE` is parsed as JSON, falling back to a string.
`save` validates before writing and writes atomically. Stacks are edited
only through the CLI or the file, never through MCP tools: a model should
not reshape its own tool access, and a change takes effect only when the
server restarts anyway.

## 8. Server behaviour

* Flags: `--stack NAME` (default `research`), `--root DIR` (default the
  current directory), `--stacks-file PATH`, `--sync-seconds S` (default 60),
  `--max-output-chars N` (default 4000), `--quiet` (no stderr output beyond
  fatal errors), `--list` (print the resolved tools and their size, then
  exit).
* **Paths.** Every path argument resolves against `--root`; absolute paths
  must lie inside it and `..` may not escape it. In Clank the root is
  `/workspace`.
* **Startup.** No kernel compiles at startup (today: 0.9 s to build the
  server). `sparsegf2 warmup` runs a tiny instance of every kernel so the
  first real call does not pay 10 to 30 s of compilation; the Clank guide
  sets `NUMBA_CACHE_DIR` to a directory in the workspace and runs it once.
* **Errors.** A `ValueError` from a handler becomes a tool error whose text
  says what to change (`degree must be even (K/2 neighbours per side), got
  5`). Anything else is reported as an internal error with the exception
  type, and logged to stderr unless `--quiet`.
* **Output.** Rendered text first, capped at `--max-output-chars` with a
  final line saying what was cut and where the full data is (`output_dir`).

## 9. Testing

* Analysis: `mean_first_failure` and `distance_bounds` on codes with known
  answers (`[[4,2,2]]`: d = 2; repetition-type codes; k = 0), agreement of
  mu_D with the direct sample mean when w = 0, the junction-dip flag.
* Graphs: `stats` against closed forms (cycle: lambda_2 = 2 - 2cos(2 pi/n),
  mean path length, clustering 0; complete graph: lambda_2 = n, clustering
  1; ring lattice of degree K: clustering 3(K - 2)/(4(K - 1))); file round
  trips and every validation error.
* Registry: the flatness and size criteria of section 2 over every stack;
  every tool has a description under 1,200 characters with an example;
  shared parameter groups are identical wherever they appear.
* Stacks: built-ins and bundles resolve; custom files parse; `include`,
  `exclude`, `fixed`, `defaults`, `*`; collisions, unknown names, cycles and
  bad values are errors; CLI save / show / delete round trip.
* Handlers: each tool on small inputs (n = 8 to 16) through the handler and
  through an MCP stdio session per built-in stack; results are under the cap
  and start with the tool name.
* Physics: `erasure_run` matches the same ensemble run through
  `MonitoredCircuit` and `analysis` directly; `traj_run` with
  `compare_stim` matches Stim; `traj_probe` reproduces `traj_run`'s codes
  exactly; the replay-contract test of 6.4.
* `scripts/eval_agent_tools.py` (not CI): about 15 requests (run an erasure

## 11. Out of scope

* The reverse log (own spec, deferred until the simulator is complete and
  tested).
* A random-code baseline rho (needs a uniform n-qubit Clifford or random
  stabilizer-code sampler; DESIGN.md roadmap).
* Streamable HTTP transport, dynamic stacks (`tools/list_changed`), editing
  stacks over MCP, sweeping two parameters at once.

## 12. Breaking changes

* MCP tool names change (section 5.9) and `sparsegf2-mcp` without `--stack`
  serves `research`, not every tool.
* Nothing else: the Python library, the JSON API and the CLI only gain
  functions and commands.
